## 3. 원격 데이터 형태 (제안)

파일명: **`passages_2026.json`** — 🔴 **연도로 나눈다.**

```json
[
  {
    "id": 20260907001,
    "title": "새벽의 도서관",
    "theme": "독서·읽기",
    "text": "새벽 도서관은 아직 아무도 오지 않아 조용했다. …",
    "chars": 204,
    "createdAt": "2026-09-07"
  }
]
```

### 왜 연도로 나누나 — 지금 퀴즈가 안고 있는 문제를 물려받지 않으려고

앱은 동기화 때마다 **파일 전체를 다시 내려받는다**(조건부 요청 없음). 퀴즈는 지금 **매 동기화 438KB**다
(`knowledge.json` 192KB + `korean.json` 97KB + `travel.json` 74KB + `trend.json` 75KB). 이 파일들은 **줄지 않는다.**

지문을 한 파일에 계속 쌓으면 같은 길을 간다:

| 하루 생산 | 1편 ≈ 750바이트(본문 200자 + 메타) | 1년 | 3년 |
|---|---|---|---|
| 1편 | 0.75KB/일 | **약 270KB** | 약 800KB |
| 2편 | 1.5KB/일 | 약 550KB | 약 1.6MB |

→ 처음부터 연도로 쪼개면 **앱은 «올해 + 작년» 2개 파일만 받으면 된다**(≈ 300~600KB 상한).
지난 연도 지문은 저장소에 그대로 남으므로 «기존 지문 보관»도 만족한다.

**하루 몇 편?** — **1편 권장.** 「오늘의 지문」이 하루 1편이면 소비 속도와 공급이 맞는다.
2편 이상 쌓이면 사용자가 못 본 지문이 계속 밀린다(퀴즈에서 이미 겪은 문제 — 그래서 `FRESH_PER_CATEGORY`가 생겼다).

## 4. 앱 안에서는 어디에 저장하나

🔴 **원격 지문과 사용자 보관함은 «다른 파일»로 둔다.**

| 데이터 | 파일 | 주인 | 삭제하면 |
|---|---|---|---|
| 사용자 보관함(기존) | `filesDir/reading_passages.json` | **사용자** | 영구 삭제 |
| 로봇 지문(신규) | `filesDir/reading_passages_remote.json` | **로봇** | 다음 동기화에 되살아난다 |
| 「본 것」 기준점(신규) | DataStore `DAILY_SEEN_PASSAGE_COUNT` | 앱 | 「새 지문 N개」가 0으로 |

**한 파일에 섞으면 안 되는 이유** — 동기화가 사용자 데이터를 건드리는 경로가 생긴다.
로봇 지문은 «갱신·교체»되는 물건이고 보관함은 «사용자가 찍어서 넣은» 물건이다.
섞어 두면 동기화 버그 한 번에 **사용자가 촬영해 넣은 지문이 날아간다.** 이건 되돌릴 수 없는 종류의 사고다.

- 사용자가 로봇 지문을 목록에서 치우고 싶어 하면 → **숨김 id 목록**만 따로 둔다(원본은 그대로).
- 사용자가 로봇 지문을 «내 것으로 보관»하고 싶어 하면 → 보관함으로 **복사**한다(그때부터 사용자 소유).
- 이미지는 없다(로봇 지문은 텍스트뿐) → `reading_pages/`는 그대로 사용자 전용.

**용량**: 로컬 캐시도 위 표 그대로(수백 KB). Room·DB는 필요 없다 — 지금의 JSON 파일 방식으로 충분하고,
`ReadingTrainingRepository`가 이미 같은 패턴(`@Synchronized` + `filesDir` JSON)을 쓰고 있다.

## 5. 「오늘의 지문」과 「새 지문이 도착했어요」

### 5-1. 오늘의 지문 = 날짜로 정해지는 1편

`DailyRecord.pickDailyIndices(date, total, count = 1, freshFrom = …)` **그대로 재사용**한다.
새로 만들 규칙이 없다 — 이미 「새로 들어온 것에 최소 한 칸」까지 들어 있고 테스트로 고정돼 있다.

- 허브 상단 카드: **「오늘의 지문」** → 읽으면 초록 **「오늘 완료」**(퀴즈 카드와 같은 문법)
- 훈련 모듈(페이서·RSVP·묶어읽기)에 그 지문이 들어간다 — 지금 `PRACTICE_PASSAGES.random()`이 하던 자리

### 5-2. 알림 문구

`BriefingReceiver.buildBriefingMessage()`에 파트를 하나 더 넣는다. 🔴 **네트워크 금지 규칙은 유지**한다 —
캐시 파일의 «개수»만 세면 되므로 통신이 필요 없다.

```
새 지문 1편 · 새 문제 5개 · 12일 연속 도전 중 — 오늘의 뉴스와 퀴즈가 기다립니다.
```

> ⚠️ **파트를 무한정 늘리면 안 된다.** 알림 한 줄이 길어지면 뒤가 잘려 아무것도 전달되지 않는다.
> **우선순위를 정한다: 새 지문 → 새 문제 → 연속일**, 최대 2파트까지만 조립.
> 「새로운 지문이 도착했어요」를 **매일 같은 문구로 쓰지 않는다** — 고정 문구는 사흘이면 알림 해제로 이어진다(리텐션 검토서의 결론).

## 6. 🔴 밀리면 의욕이 꺾인다 — 상한과 복귀 설계

> 「자주 못 들어와서 쌓이면 의욕이 떨어진다」는 지적에 대한 답. **이 절이 없으면 §5는 오히려 이탈을 만든다.**

### 6-1. 진단 — 밀리는 것은 «지문»이 아니라 «숫자»다

먼저 사실 확인: **오늘의 지문은 날짜로 정해지는 1편**이라 안 읽어도 어디에도 쌓이지 않는다(§5-1).
빚이 생기는 곳은 **카운터 하나뿐**이다. 그런데 그 카운터가 지금 설계로는 **끝없이 커진다.**

🔴 **퀴즈 쪽에는 이 상한이 이미 없다** — [`BriefingReceiver.kt:127`](../app/src/main/java/com/kitwlshcom/kdailyutil/receiver/BriefingReceiver.kt#L127):

```kotlin
val newCount = if (status.seenQuizCount > 0) (total - status.seenQuizCount).coerceAtLeast(0) else 0
```

하루 5문항이 들어오므로(실측), 사용자가 앱을 안 열면 이렇게 된다:

| 비운 기간 | 지금 나가는 알림 문구 | 지문(하루 1편)이면 |
|---|---|---|
| 7일 | 「새 문제 **35개**」 | 새 지문 7편 |
| 30일 | 「새 문제 **150개**」 | 새 지문 30편 |
| 60일 | 「새 문제 **300개**」 | 새 지문 60편 |

→ **초대가 아니라 청구서다.** 오래 비운 사람일수록 큰 숫자를 받는다 — *돌아오기 가장 어려운 사람에게 가장 큰 벽을 세우는* 구조다.
→ ✅ **vc8이 아직 스토어에 안 나갔다. 지금이 고칠 수 있는 마지막 시점이다.**

### 6-2. 조치 4개 — 겹쳐서 쓴다

| # | 조치 | 무엇을 막나 | 지문 | 퀴즈 |
|---|---|---|---|---|
| ① | **신규 창(TTL) 7일** — `createdAt` 기준으로 «최근 7일에 도착한 것»만 신규로 센다 | 카운터가 **구조적으로** 7을 못 넘는다 | ✅ 가능(날짜 있음) | ⚠️ 기존 문항에 날짜가 없다 → ②로 대신 |
| ② | **표시 상한** — 넘으면 「20개+」로 자른다 | 세 자리 숫자가 안 나온다 | 불필요(①로 충분) | ✅ `QUIZ_NEW_CAP = 20` |
| ③ | **복귀 사면** — 7일 이상 비웠다 돌아오면 **기준점을 현재값으로 리셋**하고 숫자를 아예 안 보여 준다 | 「밀린 것」 개념 자체를 지운다 | ✅ | ✅ |
| ④ | **목록 상한** — 허브의 「새 지문」 섹션은 최대 5편, 나머지는 «지난 지문»으로 조용히 내린다(삭제 아님) | 목록 스크롤이 벽처럼 보이는 것 | ✅ | — |

**상수는 `DailyRecord`에 두고 단위 테스트로 고정한다**(지금 스트릭·오늘의 퀴즈 규칙이 그렇게 돼 있다):

```kotlin
const val FRESH_WINDOW_DAYS = 7    // ① 신규로 세는 창
const val RETURN_AMNESTY_DAYS = 7  // ③ 이 이상 비우면 «다시 시작»
const val NEW_LIST_MAX = 5         // ④ 신규 섹션에 한 번에 보여 줄 최대 편수
const val QUIZ_NEW_CAP = 20        // ② 퀴즈 카운터 표시 상한
```

### 6-4. 복귀 문구 — 「며칠째」를 어떻게 쓸까

사용자 제안(«몇일째 접속 / 신규 몇 건 / 새로 시작»)을 문구 규칙으로 정리하면:

- **연속일은 살아 있을 때만 말한다** — `displayStreak()`이 이미 «이틀 넘게 비우면 0»으로 만든다([DailyRecord.kt:86](../app/src/main/java/com/kitwlshcom/kdailyutil/data/DailyRecord.kt#L86)). 0이면 **연속일을 아예 언급하지 않는다**.
- 🔴 **「끊겼습니다」·「놓친 지문 N편」은 절대 쓰지 않는다.** 죄책감 알림은 알림 해제 → 복귀 수단 영구 상실로 직행한다(리텐션 검토서의 결론).
- 복귀 첫날 문구: **「그동안 새 지문이 쌓였어요 — 오늘 한 편부터 다시 시작해요」**. 숫자를 말하지 않는다.
- 둘째 날부터 정상 문구로 돌아간다(「2일 연속」…). **다시 1일차**라는 사실은 화면의 연속일 숫자로만 조용히 드러낸다.
- 알림 조립 우선순위(§5-2)와 합치면: **복귀 사면 중이면 숫자 파트를 만들지 않는다.**

### 6-5. 「다 따라잡기」 기능을 만들지 않는 이유

「밀린 지문 30편 몰아 읽기」 같은 UI는 **빚 상환 화면**이 된다. 대신 이미 있는 장치를 쓴다:

- `pickDailyIndices(freshFrom = …)`이 **오늘 세트에 새것 한 칸을 자동 배정**한다 → 따라잡지 않아도 **새 지문은 자연히 눈에 띈다**.
- 더 읽고 싶은 사람에게는 **「한 편 더 읽기」 버튼**만 준다 — **카운터도 목표도 붙이지 않는다**. 자발적 소비는 부담이 아니지만, 진행률 막대가 붙는 순간 과제가 된다.

### 6-6. 검토했으나 권하지 않는 것

| 방안 | 판정 |
|---|---|
| 밀린 지문을 **자동 삭제** | ❌ «내가 못 본 것이 지워졌다»는 인상. 아카이브(«지난 지문»)로만 |
| **미열람 배지 숫자를 계속 표시** | ❌ 지금 퀴즈가 그렇고, 그게 §6-1의 문제다 |
| 부재자에게 **알림 횟수 늘리기** | ❌ 리텐션 검토서 「하지 말 것」. 이탈을 앞당긴다 |
| **연속 기록 복구권 판매/광고 시청** | ❌ 이 앱의 정책 방향(보상형 장치 배제)과 어긋난다 |
| 신규 창을 **3일**로 더 짧게 | 🟡 주 2~3회 여는 사람이 새 지문을 못 보게 된다. 7일이 «주 1회 사용자»까지 담는 값 |
| 신규 창을 **30일**로 길게 | 🟡 상한이 30이 되어 §6-1 문제가 축소만 될 뿐 남는다 |

## 7. 저작권 — 이미 정해 둔 선 안에 있다

[FEATURE_SPEED_READING.md §1](FEATURE_SPEED_READING.md)이 허용 경로를 셋으로 못 박아 뒀다:
① 저작권 만료 공개 텍스트 ② 사용자 본인 붙여넣기 ③ **AI 생성 원문**.
로봇 지문은 ③이다. 다만 프롬프트에 **명시적 가드**를 넣는다:

- 🔴 **실존 작품·기사·가사의 문장을 재현하지 말 것**(요약·번안도 금지). 새로 쓴 창작 산문만.
- 실존 인물·상표·특정 기업을 소재로 삼지 말 것.
- 주제는 기존 17개 주제 로테이션(독서·자연·우주·바다·기술·습관·역사·여행·요리·건강·계절·음악·도시·동물·시간·식물·경제).
- 길이 **200자 ± 50자**(현재 내장 지문이 146~213자. RSVP·페이서 한 세션에 맞는 크기다).
- 중복 가드: 퀴즈 로봇이 쓰는 방식과 동일하게 **최근 지문의 제목·첫 문장을 프롬프트에 넣어** 같은 글을 다시 쓰지 않게 한다.

## 8. 공급원이 죽어도 앱은 멀쩡해야 한다

- 원격을 하나도 못 받으면 **기존 캐시를 그대로 쓴다**(퀴즈의 last-good 규칙 그대로).
- 캐시도 비어 있으면 **내장 19편으로 떨어진다** → `PRACTICE_PASSAGES`는 **지우지 않는다**(§2-D).
- 로봇이 실패하면 `korean_quiz_data`에 **이슈가 자동으로 열린다**(이미 있는 장치). `last_run.json`에 `passages` 블록을 넣어 **지문만 실패한 경우도 보이게** 한다.
- 🔧 비상 레버는 그대로 `QUIZ_MODEL` 하나(모델이 막히면 코드 수정 없이 교체).

## 9. 하지 말 것

- ❌ **새 저장소를 만들지 말 것** — 감시 대상이 늘면 방치 기간에 조용히 죽는다(§2-B).
- ❌ **`k-series-config`에 콘텐츠를 넣지 말 것** — 비상 레버 파일이다(§2-C).
- ❌ **사용자 보관함 파일에 로봇 지문을 쓰지 말 것**(§4).
- ❌ **알림에서 통신하지 말 것** — 알림 한 줄 때문에 알림 자체를 놓치는 쪽이 훨씬 나쁘다.
- ❌ **하루 3편 이상 생산하지 말 것** — 소비 속도를 넘으면 「못 본 지문」이 쌓여 오히려 부담이 된다.
- ❌ 지문에 **AI 키를 요구하지 말 것** — 읽기 자체는 키 없이 되어야 한다(이해도 채점만 키가 필요한 지금 구조 유지).
- ❌ 🔴 **미열람 숫자를 상한 없이 보여 주지 말 것**(§6). 「새 지문 30편」은 초대가 아니라 청구서다.
- ❌ **「놓쳤다」·「끊겼다」·「밀렸다」를 화면과 알림에 쓰지 말 것** — 죄책감은 알림 해제로, 알림 해제는 영구 이탈로 이어진다.
- ❌ **밀린 분량을 자동 삭제하지 말 것** — 「지난 지문」으로 내리기만 한다(§6-6).

|---|---|---|---|
| **0** | 🔴 **퀴즈 카운터 상한**(`QUIZ_NEW_CAP`) + **복귀 사면** — §6-2 ②③ | 앱 | 「새 문제 300개」가 안 나오는지(단위 테스트) |

**0번은 나머지와 분리해서 볼 것** — 지문과 무관하게 **이미 코드에 들어가 있는 문제**다(vc8 미출시분).
넣는다면 **vc8에 같이 넣는 것이 맞다.** 안 넣고 내보내면, 두 달 비운 사용자가 「새 문제 300개」를 받는 상태로 출시된다.
🔴 다만 **vc8은 「버전코드 올리지 말고 release는 다음에」라는 지시로 멈춰 있는 상태**라 사용자 판단이 필요하다(§11-5).

**1~2번(로봇)만 먼저 해도 손해가 없다** — 앱이 아직 안 읽어도 지문은 그날부터 쌓인다.
앱이 나갈 때쯤이면 **이미 수십 편이 준비돼 있다.** 반대로 앱을 먼저 내면 빈 목록으로 출시된다.

## 11. 사용자 결정이 필요한 것

1. **하루 몇 편?** — 권고 1편(§3). 2편으로 하면 「오늘의 지문」 외에 «지난 지문 보기»가 더 필요해진다.
2. **지문 길이** — 권고 200자 ± 50자. 더 길게(400~600자) 가면 이해도 채점은 좋아지지만 RSVP 한 세션이 길어진다.
3. **알림 문구 우선순위** — 새 지문을 퀴즈보다 앞에 둘지(권고: 앞. 지문은 하루 1편이라 «새로움»이 더 또렷하다).
4. **주제** — 기존 17주제 로테이션으로 충분한지, 아니면 사용자가 관심 주제를 고르게 할지(후자는 vc10 이후).
5. ~~퀴즈 카운터 상한(§10-0번)을 vc8에 넣을지~~ → ✅ **결정: vc8에 넣는다**(사용자 판단, 2026-09-07).
   🔴 **vc8 범위가 늘었다** — 코드가 움직이므로 **실기기 확인 때 알림 문구를 다시 봐야 한다**(부록 A에 한 줄 추가 필요).
6. **상한 수치 4개** — 권고값 `FRESH_WINDOW_DAYS = 7` · `RETURN_AMNESTY_DAYS = 7` · `NEW_LIST_MAX = 5` · `QUIZ_NEW_CAP = 20`.
   근거는 §6-2·§6-6(3일은 주 2~3회 사용자를 놓치고, 30일은 상한 효과가 거의 없다).
